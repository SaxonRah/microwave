# MicroWave Pico I2S audio

MicroWave's RP2350 presentation path is a reusable **Core-1 producer + queued
PIO/DMA I2S transport**. The shared mixer still owns every logical sample; the
transport owns only real-time presentation and never knows about songs, WADs,
MUS, GENMIDI, SFX channels, or game state.

The default pipeline is:

```text
Core 0 / application
        |
        | control request
        v
safe control mailbox
        |
        v
Core 1 / MicroWave producer
        |
        | 256-frame producer chunks
        v
4-period packed I2S ring
(target: keep 2 ready)
        |
        | 512-frame periods
        v
DMA IRQ: retire/start only
        |
        v
PIO standard I2S
        |
        v
MAX98357A / PCM5102A / NS4168
```

At the default 32 kHz rate, a 512-frame DMA period is 16 ms. Core 1 builds each
period from complete 256-frame producer chunks and checks the control mailbox
between chunks. The DMA interrupt never synthesizes or mixes audio: it only
retires the previous ring entry and starts an already-ready one.

If the producer misses a deadline, the IRQ sends a pre-zeroed silence period.
It deliberately does **not** replay the previous audio period; replaying stale
audio was found to produce the much more objectionable slow/repeating sound
under heavy real-time load.

## Pins

MicroWave's Pico presentation path is standard three-wire I2S generated by PIO:

- **BCLK**: GP10 by default
- **LRCLK / LRC / WS**: GP11 by default
- **DATA / DIN / SDATA**: GP12 by default

BCLK and LRCLK are adjacent because the PIO program drives them as two side-set
pins. `lrclk` therefore must always equal `bclk + 1`. DATA can be moved
independently.

The standalone demo mixer is mono. The transport accepts mono or stereo
producers; mono input is placed into both I2S slots. For mono amplifier presets,
stereo producer input is mixed down and duplicated. PCM5102A preserves stereo
input when a stereo producer is used.

## Device presets

### MAX98357A

```bat
.\mw.bat build pico max98357a
.\mw.bat run pico max98357a swd
```

Connections:

```text
Pico GP10  -> BCLK
Pico GP11  -> LRC / LRCLK
Pico GP12  -> DIN
Pico GND   -> GND
```

No MCLK is generated or required. The standalone demo is mono in both I2S
slots, so the MAX98357A channel-selection wiring may select left, right, or an
averaged mode without changing that demo signal.

### PCM5102A

```bat
.\mw.bat build pico pcm5102a
.\mw.bat run pico pcm5102a swd
```

Connections:

```text
Pico GP10  -> BCK
Pico GP11  -> LCK / LRCK
Pico GP12  -> DIN
Pico GND   -> GND
```

Use the PCM5102A in standard-I2S format. The preset uses its three-wire mode:
there is no Pico MCLK/SCK output. On boards that expose SCK, keep it in the
board's documented no-external-clock state (commonly grounded) so the DAC can
use its BCK PLL.

The default Pico rate is **32000 Hz**. With this firmware's 16-bit stereo slots,
that is 32 BCLK periods per LRCLK and is a documented PCM5102A BCK-PLL operating
point. PCM5102A rate overrides remain limited at configure time to the existing
supported 32-BCLK/LRCLK PLL points.

### NS4168

```bat
.\mw.bat build pico ns4168
.\mw.bat run pico ns4168 swd
```

Connections:

```text
Pico GP10  -> BCLK
Pico GP11  -> LRCLK
Pico GP12  -> SDATA
Pico GND   -> GND
```

NS4168 uses standard I2S. Its CTRL pin selects left or right input channel; the
standalone mono demo appears identically in both slots.

## Reusable transport API

The generic RP2350 transport lives in:

```text
shared/rp2350/mw_pico_i2s_stream.c
shared/rp2350/mw_pico_i2s_stream.h
shared/rp2350/mw_i2s.pio
```

A firmware supplies a producer callback and hardware configuration:

```c
mw_pico_i2s_stream_config_t stream;
memset(&stream, 0, sizeof(stream));
stream.sample_rate = 32000;
stream.channels = 2;
stream.pin_bclk = 10;
stream.pin_lrclk = 11;
stream.pin_data = 12;
stream.pio_index = 1;
stream.state_machine = 0;
stream.dma_channel = -1; /* claim any unused channel */
stream.output_mode = MW_PICO_I2S_OUTPUT_STEREO;
stream.producer = my_audio_producer;
stream.producer_user = my_state;

if (!mw_pico_i2s_stream_start(&stream)) {
    /* transport could not claim/configure hardware */
}
```

The producer callback always runs on Core 1 and returns the number of frames it
actually produced. Any unproduced remainder becomes silence.

### Safe audio-core control

`mw_pico_i2s_stream_run_control()` runs a callback on Core 1 at a complete
producer-chunk boundary. It is intended for state transitions that must be
serialized with rendering, such as changing a synth bank, starting/stopping a
song, or changing audio-owned mixer state.

```c
mw_pico_i2s_stream_run_control(apply_change, persistent_request, 250000u);
```

Only one synchronous control request may be outstanding. If the wait times out,
the published callback is not revoked because Core 1 may already be entering
it. Therefore the callback payload must remain valid until a late completion is
possible; persistent request storage is the safest pattern.
`mw_pico_i2s_stream_control_pending()` lets a caller that reuses that storage
wait until a timed-out request has really finished before modifying it again.

### Diagnostics

`mw_pico_i2s_stream_get_diag()` exposes:

- underrun count;
- refill count;
- last/minimum/rolling-average/maximum refill time;
- ring ready depth;
- ring low/high-water marks;
- period duration;
- control timeout count;
- Core-1 stack size and measured high-water use;
- transport/Core-1 state.

The standalone serial `PING` response includes the most useful values.

## Build options

The established device/pin options remain available. `block` still controls the
short producer/mixer chunk. The queued transport adds separate period/ring
settings.

```bat
.\mw.bat build pico max98357a rate=48000
.\mw.bat build pico ns4168 block=128
.\mw.bat build pico pcm5102a bclk=14 lrclk=15 data=16
.\mw.bat build pico max98357a sys=300000
.\mw.bat build pico max98357a MW_PICO_PERIOD=512 MW_PICO_RING_COUNT=4 MW_PICO_RING_TARGET=2
.\mw.bat build pico all
```

Available friendly options:

| option | default | meaning |
| --- | ---: | --- |
| `rate=N` | 32000 | I2S sample rate |
| `block=N` | 256 | Core-1 producer/mixer chunk in frames |
| `bclk=N` | 10 | BCLK GPIO |
| `lrclk=N` | 11 | LRCLK GPIO; must equal BCLK+1 |
| `data=N` | 12 | DATA/DIN/SDATA GPIO |
| `sys=N` | 0 | RP2350 system clock in kHz; 0 keeps board default |
| `pio=N` | 0 | PIO block, 0 or 1 |
| `sm=N` | 0 | PIO state machine, 0..3 |
| `dma=N` | 0 | fixed DMA channel; `-1` claims any unused channel |
| `serial=ON/OFF` | ON | USB status, `PING`, and `VOL` service |

Additional transport cache variables can be passed directly because `mw.bat`
already forwards any `MW_...=value` option:

| cache variable | default | meaning |
| --- | ---: | --- |
| `MW_PICO_PERIOD` | 512 | DMA period in frames |
| `MW_PICO_RING_COUNT` | 4 | total period slots |
| `MW_PICO_RING_TARGET` | 2 | ready periods Core 1 targets |
| `MW_PICO_CORE1_STACK_BYTES` | 8192 | dedicated Core-1 stack |

To configure one preset into `microwave\build` for the Pico VS Code extension:

```bat
.\mw.bat build pico max98357a vscode
```

## Flash / run

`run pico` builds the requested preset with USB serial enabled and then flashes
it. The default method is SWD through the same Pico OpenOCD/CMSIS-DAP setup used
by the VS Code extension:

```bat
.\mw.bat run pico max98357a
.\mw.bat run pico pcm5102a swd
.\mw.bat run pico ns4168 picotool
.\mw.bat run pico max98357a manual
```

SWD falls back to manual BOOTSEL if OpenOCD is unavailable or programming
fails. `picotool` likewise falls back to manual BOOTSEL.

The serial-enabled firmware answers `PING` with an `MWPICO1` line so the runner
can distinguish the application CDC port from a CMSIS-DAP probe that happens
to use the same Raspberry Pi USB vendor ID.

## Why the ring transport exists

The earlier standalone Pico frontend was intentionally simple: render one
buffer while DMA drained another, then wait for that DMA period to complete.
That path worked for the demo but did not provide enough timing isolation once
MicroWave was exercised under a substantially heavier real-time game/render
load.

The queued transport keeps synthesis off the IRQ path, gives Core 1 sole
ownership of the producer state, absorbs normal render jitter with ready audio,
and turns a missed deadline into a short silence dropout rather than repeated
stale sound. The shared mixer still has no knowledge of PIO, DMA, Core 1, or any
specific I2S device.
